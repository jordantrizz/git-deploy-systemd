# git-deploy-systemd

An inotify-based, systemd-managed `git pull` deploy watcher.

Point it at one or more git working trees. When a `.git-pull-trigger` file is
created or touched in a watched repo, the watcher runs `git pull` as the
configured user and logs the result — including git's own output — to the
systemd journal, so a failed deploy is never silent.

## How it works

- A generated watcher (`/opt/git-deploy/git-deploy-watcher.sh`) watches each
  registered repo with `inotifywait` for changes to `.git-pull-trigger`.
- On an event it runs `git pull` as the site's user, logs the outcome, writes
  optional deploy metadata for WordPress, then removes the trigger file.
- The watcher runs under `git-deploy-watcher.service` and is regenerated by the
  CLI whenever sites change.

## Quick install

One line, no checkout required:

```bash
curl -fsSL https://raw.githubusercontent.com/jordantrizz/git-deploy-systemd/main/install.sh | sudo bash
```

Pass flags through as needed, e.g. `| sudo bash -s -- --force`. Set
`GIT_DEPLOY_REF` to install a different branch or tag, or `GIT_DEPLOY_BASE_URL`
to install from a mirror.

## Install from a checkout

```bash
sudo bin/git-deploy-systemd install
```

This installs the binary to `/usr/local/sbin/git-deploy-systemd`, creates
`/opt/git-deploy/` (watcher + config), writes the systemd unit, installs
`inotify-tools` if missing, and enables the service. After that, use the CLI by
name:

```bash
sudo git-deploy-systemd install
```

## Register a site

```bash
sudo git-deploy-systemd add --path /var/www/site1 --user www-data
echo ".git-pull-trigger" >> /var/www/site1/.gitignore
```

`add` validates that the path is a git repository and that the user exists, then
creates the trigger file and regenerates the watcher.

## Trigger a deployment

```bash
touch /var/www/site1/.git-pull-trigger
```

## Check status and logs

```bash
sudo git-deploy-systemd           # status summary (default command)
sudo git-deploy-systemd list      # registered sites
sudo git-deploy-systemd version   # installed version
sudo journalctl -u git-deploy-watcher.service -n 100 --no-pager
```

On a failed pull the journal contains the exit code and git's error output, for
example:

```
FAILURE: git pull for site1 (/var/www/site1) (exit 128)
FAILURE site1: fatal: not a git repository (or any of the parent directories): .git
```

## Update

The CLI can update itself from the project's git repo or a URL:

```bash
sudo git-deploy-systemd update                    # recorded upstream URL
sudo git-deploy-systemd update --from-git         # shallow-clone upstream
sudo git-deploy-systemd update --from-url <url> --sha256 <hash>
sudo git-deploy-systemd update --from <path>      # local file
```

## Adopt an existing install

If a server was set up before version tracking or self-update existed, adopt it
in place — configuration is preserved and existing files are backed up first:

```bash
sudo git-deploy-systemd adopt --force
```

## Manage sites

```bash
sudo git-deploy-systemd add --path /var/www/site2 --user www-data --name site2
sudo git-deploy-systemd remove /var/www/site2
sudo git-deploy-systemd restart
```

## WordPress integration

An optional must-use plugin (`bin/git-deploy-systemd.php`) adds a **Tools →
Git Deploy** page and a REST endpoint for triggering deploys:

```bash
sudo git-deploy-systemd plugin add --path /var/www/site1 --label site1
sudo git-deploy-systemd plugin update
```

## Uninstall

```bash
sudo git-deploy-systemd uninstall
```

## Files

| Path | Purpose |
|------|---------|
| `/usr/local/sbin/git-deploy-systemd` | CLI command |
| `/opt/git-deploy/config/sites.conf` | Site configuration |
| `/opt/git-deploy/config/install.conf` | Install record (source + version) |
| `/opt/git-deploy/git-deploy-watcher.sh` | Generated watcher (inotifywait loop) |
| `/etc/systemd/system/git-deploy-watcher.service` | systemd service unit |
| `/etc/sudoers.d/git-deploy` | sudoers entries for watched sites |

## Commands

```bash
git-deploy-systemd            # show status
git-deploy-systemd install    # install service and dependencies
git-deploy-systemd adopt      # take over an existing install
git-deploy-systemd uninstall  # remove service and configuration
git-deploy-systemd add        # register a site
git-deploy-systemd remove     # unregister a site
git-deploy-systemd list       # list registered sites
git-deploy-systemd version    # print the installed version
git-deploy-systemd restart    # regenerate watcher and restart the service
git-deploy-systemd update     # update the binary
git-deploy-systemd update-all # update binary + WordPress mu-plugin
git-deploy-systemd plugin     # manage mu-plugin installs
git-deploy-systemd help       # full help
```

## Development

```bash
shellcheck -S warning bin/git-deploy-systemd install.sh
php -l bin/git-deploy-systemd.php
bash tests/test-git-deploy-systemd.sh
```

The test suite runs unprivileged in a temp sandbox (`GIT_DEPLOY_PREFIX` +
`GIT_DEPLOY_TESTING`); it makes no changes to the host.
